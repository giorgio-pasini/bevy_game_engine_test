Part 0 · Orientation

What Rust is, stated against Python

Four differences explain almost everything that will feel strange. Each one is a deliberate trade: you give up convenience, you get speed and compile-time guarantees.

PythonRustWhy it matters to you
Interpreted, runs immediatelyCompiled ahead of time to a native binaryThis is why you waited 21 minutes. It's also why Snake runs at hundreds of FPS.
Garbage collector frees memoryNo GC. Memory is freed when its owner goes out of scopePart 3. This is the one genuinely new idea.
Types checked at runtimeTypes checked at compile time, and inferred aggressivelyWhole classes of bug become impossible to write.
None can appear anywhereNo null. Absence is a type: Option<T>Part 4. You literally cannot forget to handle it.

note: Rust has no runtime and no interpreter. A compiled Snake binary depends on nothing but the OS.

03

Ownership and borrowing

The heart of the language, and the only part with no Python equivalent. If you have written C++ with unique_ptr and RAII, you already know most of it.

Part 3 · Ownership

Every value has exactly one owner

When the owner goes out of scope, the value is freed. No GC, no reference counting, no pause — the compiler inserts the cleanup at the closing brace.

note: after line 248, the local body is gone. Ownership moved into the Snake. Touching body afterwards is a compile error, not a runtime surprise.

warning: in Python, a = b makes two names for one list. In Rust it makes b unusable. This is the assignment that breaks Python intuition hardest.

help: C++ analogy: this is std::move, except it is the default rather than something you opt into.

Part 3 · Ownership

...unless the type is Copy

Small, fixed-size values sitting entirely on the stack can opt out of move semantics. Pos does.

note: Pos is 8 bytes. Copying it is cheaper than reasoning about who owns it, so Copy is the right call.

warning: Vec can never be Copy. It owns memory on the heap, and two owners would mean a double free. This is exactly the bug class Rust exists to eliminate.

help: rule of thumb — Copy for small stack-only values, move for anything owning heap memory.

Part 3 · Ownership

Borrowing: access without taking ownership

Moving into every function would be unusable. Instead you lend a reference: &T to read, &mut T to modify.

--> read that signature as a contract

note: &mut Commands — "I will modify this, but I am not keeping it."

note: &[Pos] — "I will only read this, and I am not keeping it."

help: the caller at line 245 must say so too: spawn_food(&mut commands, &mut rng.0, &occupied). Borrowing is explicit on both sides — you can never be surprised about which functions mutate your data.

warning: in Python every argument is passed this way invisibly, and whether a function mutates your list is something you discover by reading its body. Here it is in the type.

Part 3 · Ownership

The one rule that governs all of it

At any moment, for any piece of data, you may have either any number of readers or exactly one writer. Never both.

note: push may reallocate the vector, which would leave first pointing at freed memory. In C++ this compiles and is a dangling pointer. Here it is a compile error.

help: this rule also makes data races impossible to write, which is why Bevy can run your systems across threads without you thinking about locks.

warning: you will fight this rule early on. Every fight is the compiler pointing at a real aliasing bug you would otherwise have shipped.

Part 3 · Ownership

Slices: a borrowed window onto a sequence

Python — copies

Rust — borrows

note: a slice is a pointer plus a length. Slicing allocates nothing and copies nothing, however large the vector.

note: because it borrows, the slice cannot outlive old — and the compiler enforces that. This is why Rust needs no GC to stay memory-safe.

Part 3 · Checkpoint

Checkpoint — move or copy?

Why does (a) leave old usable, while assigning snake.body to a new variable would not?

(a) old is a Vec<Pos>, and Pos derives Copy. Indexing yields a duplicate of those 8 bytes, so old is untouched.

(b) snake.body is a Vec<Entity>, which owns heap memory and therefore cannot be Copy. Writing let b = snake.body; would try to move a field out of a borrowed struct — and the compiler rejects it outright.

The general test: does this type own anything on the heap? If yes, it moves. If it is a small stack-only value, it can be Copy.

Traits and generics

How Rust does polymorphism without inheritance — and what all those #[derive(...)] lines in your file are actually doing.

Part 5 · Traits

Traits: shared behaviour without a base class

A trait is a set of methods a type promises to provide. Closest to a Java or C# interface — but a type can gain one after the fact, without touching its definition.

LanguageMechanismChecked
PythonDuck typing — call it and hopeAt runtime, on the failing line
Java / C#implements, declared on the classCompile time, but only where you own the class
Rustimpl Trait for Type, declared anywhereCompile time, and works for types you did not write

note: there is no inheritance in Rust. No base classes, no super(), no overriding. Shared behaviour is always a trait.

help: you already used one. rand::RngExt is a trait, and line 13's use rand::RngExt; is what makes rng.random_range(..) exist at line 216. Import the trait or the method is invisible — a common early stumbling block.

Part 6 · Checkpoint

Checkpoint — what breaks without move?

Why does the compiler reject this, in terms of Part 3?

Without move, the inner closure borrows x from the outer closure's stack frame.

But flat_map does not consume the inner iterator immediately — it returns it, to be drained later, after the outer closure has already returned and its frame is gone. The borrow would outlive what it points at.

That is a use-after-free, and in C++ it would compile silently and corrupt memory at random. Rust rejects it: error[E0373]: closure may outlive the current function, but it borrows `x`.

move copies x into the closure so it owns its own copy — and since x is an i32, that copy is free.
